# Feat Review & Design

## 目的

- 对已有的feat需求文档进行Review，检查完整性和可行性
- 如有问题，提出澄清问题并等待用户确认
- 问题解决后，根据范围分类生成对应的详细设计文档（后端/前端/全栈）

## 工作流

### 1) 定位feat文档

- 如果用户指定了文档路径，直接读取
- 否则列出 `docs/feat/` 目录下的文档供用户选择
- 优先选择最近修改的文档

### 2) Review需求文档

执行以下检查项：

#### 2.1 完整性检查
| 检查项 | 说明 |
|--------|------|
| 功能概述 | 背景、目标、非目标是否清晰 |
| 使用场景 | 用户角色、场景流程是否完整 |
| 接口定义 | 输入输出参数、错误码是否明确 |
| 实体设计 | 涉及的数据模型是否说明 |
| 验收标准 | AC是否可测试、可验证 |

#### 2.2 可行性检查（概念层面）

> 详细的代码级验证（方法签名匹配、文件路径存在、依赖可用性）由 `design-review-dev` 统一负责。

| 检查项 | 说明 |
|--------|------|
| 技术可行性 | 是否有明显的技术障碍 |
| 架构兼容性 | 是否与现有架构设计冲突 |
| 安全考虑 | 认证、授权、数据安全需求 |

#### 2.3 一致性检查
| 检查项 | 说明 |
|--------|------|
| 术语一致 | 同一概念是否使用相同术语 |
| 参数一致 | 接口参数与实体字段是否匹配 |
| 流程一致 | 场景描述与接口设计是否对应 |

### 2.5) 范围分类

在 Review 完成后、生成设计前，分析 feat 内容确定设计范围：

| 范围 | 识别信号 | 输出 |
|------|----------|------|
| 仅后端 | API、数据库、模型、迁移、业务规则，无 UI/页面描述 | 1 份 backend-design |
| 仅前端 | 页面、表单、列表、UI、交互、用户界面，无 API/模型变更 | 1 份 frontend-design |
| 全栈 | 两者兼有（既有 API/模型变更，又有页面/UI 描述） | 2 份（backend + frontend） |

**分类规则**：
- 检查 feat 文档中是否包含后端信号词：API、endpoint、数据库、表、模型、迁移、migration、service、repository
- 检查 feat 文档中是否包含前端信号词：页面、表单、列表、UI、界面、交互、按钮、弹窗、导航、路由、组件
- 两者都有 → 全栈；仅有一方 → 对应范围
- **不确定时询问用户确认**

### 2.6) Codex Auto-Review Loop（最多 3 轮）

在 Claude 初步 Review 和范围分类之后，启动 Codex Review 迭代，**每轮结束后检查是否还有阻塞/严重问题，若无则立即停止并进入设计阶段**：

**执行规则**：
- 每轮调用 Codex CLI `task` 命令，传入 `assets/codex-reviewer-prompt.md` 作为系统 prompt + feat 文档内容
- **Round 1**：
  - Codex 审查 feat 文档
  - Claude 解析结果：若**无阻塞问题且无严重问题** → **直接进入 §4 设计阶段**，不再进行 Round 2/3
  - 若存在阻塞/严重问题 → 按 §2.4 判定是否自动修正 → 进入 Round 2 或 §3
- **Round 2**：
  - 基于修正后的文档，Codex 再次审查
  - Claude 解析结果：若**无阻塞问题且无严重问题** → **直接进入 §4 设计阶段**，不再进行 Round 3
  - 若仍存在阻塞/严重问题 → 按 §2.4 判定 → 若全部可自动修正则应用后进入 Round 3；若存在不得自动假设的问题则进入 §3
- **Round 3**（安全网）：
  - Codex 做最终审查，只输出问题清单
  - **不再自动修改文档**
  - 进入 §2.7 自动分支判定

- 所有修正操作使用 `Edit` 工具直接修改原 feat 文档，不创建副本

**Codex CLI 调用示例**：
```bash
PROMPT_FILE="assets/codex-reviewer-prompt.md"
FEAT_FILE="<feat-doc-path>"
ROUND="<X>"

node "${CLAUDE_PLUGIN_ROOT}/scripts/codex-companion.mjs" task --wait \
  "$(cat "$PROMPT_FILE")

当前是 Round ${ROUND}/3。
以下是 feat 文档内容：
---
$(cat "$FEAT_FILE")
"
```

**可用性检查**：
- 检查项：`CLAUDE_PLUGIN_ROOT` 环境变量已设置且对应路径包含可执行的 `codex-companion.mjs`、`task` 子命令支持 `--wait` 能力
- 任一检查失败均按 plugin 异常降级处理（进入 §3 用户确认），已执行轮次记为 **0**

**输入边界与调用前校验**：
- 传输能力边界：0–200KB（含边界值）的 UTF-8 编码可读 Markdown 文本均可传入 plugin
- **调用前输入校验失败**：空路径、无法读取、非文本内容、编码异常、大小超过 200KB 时，均按调用前输入校验失败处理（已执行轮次 0，进入 §3）；空文档（0KB 可读文件）不归入调用前输入校验失败，而按文档内容缺陷处理

**plugin 执行失败**：
- 已成功发起 plugin 调用后，出现非零退出码、超时（默认 300s）、空输出或无法解析为结构化 Markdown，均视为 plugin 执行失败
- **特别规定**：任一必需段落缺失、表格不可解析、占位符未替换、输出为空、Round 1/2 的阻塞/严重问题修正建议为空/"无"，均视为 **plugin 执行失败**，不得将其归类为文档的阻塞/严重问题，也不得触发自动修正
- plugin 执行失败时，记录失败原因并直接进入 §3 用户确认环节，不得自动进入设计阶段

**自动修正原则**：
- 仅修正文档中的缺失、不一致、模糊之处
- 不添加实现细节（代码、API schema、数据库设计保留在设计阶段）
- **基于假设的补全仅限**：非核心、非业务、可由同一文档上下文唯一推导但原文未显式写出的信息；凡不能唯一推导的内容一律不得自动补全
- 允许基于假设补全时，在文档末尾添加一行 `<!-- Codex Review 自动补全：{原因} -->`
- 涉及权限模型、数据保留策略、外部系统行为、核心业务规则且文档无明确依据的，**一律不得自动补全**

**自动修正分级规则**：
- **判定优先级**：凡无法从同一文档内找到唯一、明确的推导依据的内容，一律不得自动补全
- **可直接自动修正**：
  - 术语不一致（文档 A 处叫 "userId"，B 处叫 "user_id"）
  - 缺失但可从文档上下文唯一推导的 AC（文档已描述删除操作，但 AC 中遗漏"删除成功返回 200"）
  - 非业务性边界描述（如空结果需有明确返回语义、错误时需展示/返回可识别失败原因）
  - 格式不统一（表格列名不一致、编号重复）
  - 表述性补充（如将"等"明确为文档中已列出的具体项）
- **不得自动假设，必须残留**：
  - 涉及权限模型（如"管理员可查看全部数据"——若文档未定义角色权限体系）
  - 数据保留策略（如"删除后保留 30 天"——若文档未提及保留期）
  - 外部系统行为（如"支付成功后异步回调"——若文档未定义回调协议和重试策略）
  - 核心业务规则且文档无明确依据（如"退款金额不得超过原订单金额"——若文档未定义退款约束）
  - 此类问题作为阻塞/严重问题进入 §3 用户确认

**解析规则**：
- 严格依据 §2.3 结构化输出契约进行解析
- 以 `阻塞问题`、`严重问题`、`改进项` 三个 Markdown 表格为唯一判定来源
- 表格无数据时必须使用固定空值标记：`| - | 无 | - | - |`
- 出现占位符示例行（如 `{一句话描述}` 未替换）或无法解析表格时，视为 plugin 执行失败
- 任一必需段落缺失即视为不可解析（plugin 执行失败）
- **解析边界**：问题单元格不得包含管道符 `|`（禁止出现，无需转义）；单元格内不得换行；重复必需段落视为不可解析；允许段落间空白行；表格必须包含表头、分隔行和至少一条数据行（空值标记 `| - | 无 | - | - |` 算一条有效数据行）
- **修正建议有效性**：Round 1/2 中，阻塞/严重问题的修正建议不得为空、"无"或纯描述性文本；若缺少可操作修正建议，一律视为 plugin 输出不可解析，按 plugin 执行失败处理
- 不得从自由文本推断通过
- 所有不可解析情况均按 plugin 异常降级处理，不得触发自动修正

**自动修正写入失败处理**：
- 修正前记录原文摘要
- 每次修正必须记录：轮次、章节、原问题、修正摘要、是否已写入、失败原因
- 若自动修正无法成功写入原 feat 文档 → 停止 Codex Auto-Review Loop，输出失败原因和未应用建议，进入 §3
- 不得继续下一轮或进入设计阶段

### 2.7) 自动分支判定

**Round 1 或 Round 2 结束后**（若 Codex Review Loop 提前终止）：
- 条件：**无阻塞问题 + 无严重问题**
- 行为：**自动进入 §4 生成详细设计文档**

**Round 3 结束后**（仅在 Round 2 仍有残留问题时进入）：
- 条件：**无阻塞问题 + 无严重问题** → 自动进入 §4 生成详细设计文档
- 条件：**存在阻塞问题或严重问题** → 进入 §3 用户确认环节

**改进项处理**：
- 改进项不阻塞流程
- 汇总所有改进项，在输出中展示供用户参考；只展示最终一轮仍然存在的改进项，避免把已修正或已失效的问题当作当前建议
- 不在 feat 文档中自动修改改进项

### 3) 用户确认（仅存在阻塞/严重问题时）

- 将发现的问题按严重程度分类：
  - **阻塞问题**：必须解决才能开始设计
  - **严重问题**：会对后续实现造成困扰，处理不好大概率阻塞
  - **改进项**：有改进更好，没有也不会对需求或设计有大的影响
- **Codex 自动修正摘要**：展示 Loop 1/2 中已自动应用的所有修正，让用户知情
- 以问题清单形式呈现，等待用户逐一确认或澄清
- 用户回答后更新 feat 文档
- 所有阻塞和严重问题解决后，方可进入 §4 设计阶段

**§3 用户确认输出契约**：

无论因何种原因进入 §3 用户确认环节，输出必须包含以下固定字段：

1. **进入 §3 的原因**：残留阻塞问题 / 残留严重问题 / plugin 执行失败 / 自动修正写入失败 / Round 1/2 存在不得自动假设问题 / 调用前输入校验失败 / plugin 可用性检查失败
2. **已执行轮次**：Codex Auto-Review Loop 实际执行了多少轮；可用性检查失败且未发起 plugin 调用时记为 0 轮；Round 1 停止时记为 1 轮；以此类推
3. **Codex 自动修正摘要**：已应用的修正清单，或无修正的原因说明
4. **问题清单**：按进入原因区分展示内容
   - Round 3 后：展示"最终 Review 问题清单"（基于 Round 3 输出）
   - Round 1/2 未复审场景：展示"未处理的原 Review 问题清单"（基于原 Review 输出）
   - 问题表格含：问题摘要、文档位置、修正建议
5. **用户可选动作**：根据原因类型提供的固定选项

**失败原因枚举与对应 §3 动作**：

| 失败原因 | 说明 | 已执行轮次 | 用户可选动作 |
|---------|------|------------|-------------|
| 残留阻塞问题 | Round 3 后仍有阻塞问题 | 3 轮 | 补充/修正文档后重试 Review / 停止 |
| 残留严重问题 | Round 3 后仍有严重问题 | 3 轮 | 修正后重试 Review / 接受风险并记录说明后进入设计 / 停止 |
| Round 1/2 存在不得自动假设问题 | 有可修正项已应用，但残留问题含不得自动假设项 | 实际发起轮次 | 修正后重试 Review / 停止 |
| 调用前输入校验失败 | 文档超过 200KB、编码异常、不可读、空路径 | 0 轮 | 修正输入后重试 Codex Review / 跳过 Codex 改走 Claude 原 Review 流程 / 停止 |
| plugin 可用性检查失败 | `CLAUDE_PLUGIN_ROOT` 未设置、脚本不可执行、子命令不支持 | 0 轮 | 重试 Codex Review / 跳过 Codex 改走 Claude 原 Review 流程 / 停止 |
| plugin 执行失败 | plugin 非零退出、超时、空输出、输出不可解析 | 实际发起轮次 | 重试 Codex Review / 跳过 Codex 改走 Claude 原 Review 流程 / 停止 |
| 自动修正写入失败 | 修正无法成功写入原 feat 文档 | 实际发起轮次 | 重试 Codex Review / 跳过 Codex 改走 Claude 原 Review 流程 / 停止 |

**约束与闭环规则**：
- 跳过时不得标记为 Codex Review 通过
- 残留阻塞问题不得在未重新 Review 的情况下直接进入设计
- 自动修正一旦成功写入即保留，不提供回滚；在 §3 输出中必须明确标注"已写入的自动修正已保留在 feat 文档中"
- **重新 Review 规则**：因不得自动假设的问题进入 §3 后，用户修正文档后必须重新启动 Codex Review（从 Round 1 开始）；重试 Review 的输入必须是包含已保留自动修正和用户新增修正后的当前 feat 文档
- **只有经过 Round 3 最终审查后且仅残留严重问题时，才允许用户接受风险并记录说明后进入设计阶段**；阻塞问题永远不得通过风险接受跳过
- Round 1/2 因不得自动假设停止时，只允许"修正后重试 Review"或"停止"，不得直接接受风险进入设计

**跳过 Codex 后的路径**：
- 用户选择跳过后，恢复 `feat-review-design` 原 §3/§4 流程（Claude 进行 Review → 用户确认 → 生成设计）
- Claude 原 Review 的输入必须是当前 feat 文档，包含所有已成功写入的自动修正
- Claude 原 Review 仍必须满足**无阻塞问题**方可进入设计
- 若存在严重问题，用户可选择接受风险并记录说明后进入设计；风险说明必须写入最终输出和 design 文档前置说明
- 若通过，输出标记为 "Claude Review 通过（Codex Review 已跳过）"

### 4) 生成详细设计

本阶段可由 §2.7 自动触发（无阻塞/严重问题），也可由用户确认后触发（已解决残留问题）。根据步骤 2.5 的范围分类生成对应的设计文档：

#### 4a) 后端设计（含后端范围时生成）

使用 `assets/backend-design-template.md` 模板，包含：

- **接口设计**：新增/变更 API、输入/输出/错误码、内部接口
- **模型设计**：新增/变更实体、实体关系、数据迁移
- **逻辑设计**：核心业务流程（ASCII 流程图）、业务规则、边界/异常处理
- **测试方案**：测试策略（单元/大单元/E2E）、关键用例
- **影响评估**：对现有功能影响、对其他模块影响、回滚方案

**接口设计强制要求**：
- feat 文档不包含 API 设计（模板禁止写入），接口需**从用户场景和验收标准推导**：每个用户场景需要哪些操作 → 对应哪些 API endpoint
- 推导出所有 API 后，**不允许留空或使用占位符**，每个 API 必须定义：HTTP 方法、路径、认证要求、完整 Request 结构（字段名/类型/是否必填/约束）、完整 Response 结构（200 及常见非 200）、错误码表（错误码/HTTP Status/说明）
- 如果用户场景描述不足以推导接口（如输入输出字段不明确），应在 Codex Review Loop 中自动补全；若 Loop 结束后仍模糊，在 §3 确认阶段由用户最终确认

#### 4b) 前端设计（含前端范围时生成）

使用 `assets/frontend-design-template.md` 模板，包含：

- **设计概述**：目标、设计约束（响应式、无障碍、性能指标）
- **页面原型**：页面清单表 + 每页 ASCII Art 线框图 + 页面交互关系（流转图/数据传递/入口出口条件）
- **组件层次结构**：组件树（ASCII 缩进）+ 共享组件表 + 页面专属组件表
- **状态管理设计**：状态分层表（服务端/URL/表单/UI/全局）+ 状态流转图
- **数据获取策略**：API 依赖表 + SSR/CSR 决策表 + 加载/空/错误状态表
- **路由设计**：路由表 + 导航流程图 + 受保护路由
- **交互流程**：关键交互序列（ASCII）+ 表单校验规则表
- **响应式设计**：断点策略表 + 关键适配说明
- **测试方案**：测试策略表（组件/E2E/视觉）+ 关键用例表
- **影响评估**：对现有前端影响 + 后端接口依赖 + UI Spec 生成指引表

#### 4c) 全栈交叉引用

全栈范围时，两份文档互相交叉引用：
- backend-design 头部的「关联前端设计」指向 frontend-design 文件路径
- frontend-design 头部的「关联后端设计」指向 backend-design 文件路径

### 5) 输出设计文档


- 仅后端 → `docs/modules/auth/design/020-user-oauth-backend-design.md`

- 全栈 → 两个文件都生成
