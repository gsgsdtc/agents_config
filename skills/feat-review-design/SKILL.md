# Feat Review & Design

## 目的

- 对已有的feat需求文档进行Review，检查完整性和可行性
- 如有问题，提出澄清问题并等待用户确认
- 问题解决后，根据范围分类生成对应的详细设计文档（后端/前端/全栈）

## 工作流

### 1) 定位feat文档

- 如果用户指定了文档路径，直接读取
- 否则列出 `docs/feat/` 目录下的文档供用户选择
- 优先选择最近修改的文档

### 2) Review需求文档

执行以下检查项：

#### 2.1 完整性检查
| 检查项 | 说明 |
|--------|------|
| 功能概述 | 背景、目标、非目标是否清晰 |
| 使用场景 | 用户角色、场景流程是否完整 |
| 接口定义 | 输入输出参数、错误码是否明确 |
| 实体设计 | 涉及的数据模型是否说明 |
| 验收标准 | AC是否可测试、可验证 |

#### 2.2 可行性检查（概念层面）

> 详细的代码级验证（方法签名匹配、文件路径存在、依赖可用性）由 `design-review-dev` 统一负责。

| 检查项 | 说明 |
|--------|------|
| 技术可行性 | 是否有明显的技术障碍 |
| 架构兼容性 | 是否与现有架构设计冲突 |
| 安全考虑 | 认证、授权、数据安全需求 |

#### 2.3 一致性检查
| 检查项 | 说明 |
|--------|------|
| 术语一致 | 同一概念是否使用相同术语 |
| 参数一致 | 接口参数与实体字段是否匹配 |
| 流程一致 | 场景描述与接口设计是否对应 |

### 2.5) 范围分类

在 Review 完成后、生成设计前，分析 feat 内容确定设计范围：

| 范围 | 识别信号 | 输出 |
|------|----------|------|
| 仅后端 | API、数据库、模型、迁移、业务规则，无 UI/页面描述 | 1 份 backend-design |
| 仅前端 | 页面、表单、列表、UI、交互、用户界面，无 API/模型变更 | 1 份 frontend-design |
| 全栈 | 两者兼有（既有 API/模型变更，又有页面/UI 描述） | 2 份（backend + frontend） |

**分类规则**：
- 检查 feat 文档中是否包含后端信号词：API、endpoint、数据库、表、模型、迁移、migration、service、repository
- 检查 feat 文档中是否包含前端信号词：页面、表单、列表、UI、界面、交互、按钮、弹窗、导航、路由、组件
- 两者都有 → 全栈；仅有一方 → 对应范围
- **不确定时询问用户确认**

### 3) 提出问题（如有）

- 将发现的问题按严重程度分类：
  - **阻塞问题**：必须解决才能开始设计
  - **重要问题**：影响设计质量，建议解决
  - **建议项**：可优化的点，可选解决
- 以问题清单形式呈现，等待用户逐一确认或澄清
- 用户回答后更新feat文档

### 4) 生成详细设计

当所有阻塞问题解决后，根据步骤 2.5 的范围分类生成对应的设计文档：

#### 4a) 后端设计（含后端范围时生成）

使用 `assets/backend-design-template.md` 模板，包含：

- **接口设计**：新增/变更 API、输入/输出/错误码、内部接口
- **模型设计**：新增/变更实体、实体关系、数据迁移
- **逻辑设计**：核心业务流程（ASCII 流程图）、业务规则、边界/异常处理
- **测试方案**：测试策略（单元/大单元/E2E）、关键用例
- **影响评估**：对现有功能影响、对其他模块影响、回滚方案

**接口设计强制要求**：
- feat 文档不包含 API 设计（模板禁止写入），接口需**从用户场景和验收标准推导**：每个用户场景需要哪些操作 → 对应哪些 API endpoint
- 推导出所有 API 后，**不允许留空或使用占位符**，每个 API 必须定义：HTTP 方法、路径、认证要求、完整 Request 结构（字段名/类型/是否必填/约束）、完整 Response 结构（200 及常见非 200）、错误码表（错误码/HTTP Status/说明）
- 如果用户场景描述不足以推导接口（如输入输出字段不明确），在 §3 提问阶段先补全场景，不要带着模糊的接口进入设计

#### 4b) 前端设计（含前端范围时生成）

使用 `assets/frontend-design-template.md` 模板，包含：

- **设计概述**：目标、设计约束（响应式、无障碍、性能指标）
- **页面原型**：页面清单表 + 每页 ASCII Art 线框图 + 页面交互关系（流转图/数据传递/入口出口条件）
- **组件层次结构**：组件树（ASCII 缩进）+ 共享组件表 + 页面专属组件表
- **状态管理设计**：状态分层表（服务端/URL/表单/UI/全局）+ 状态流转图
- **数据获取策略**：API 依赖表 + SSR/CSR 决策表 + 加载/空/错误状态表
- **路由设计**：路由表 + 导航流程图 + 受保护路由
- **交互流程**：关键交互序列（ASCII）+ 表单校验规则表
- **响应式设计**：断点策略表 + 关键适配说明
- **测试方案**：测试策略表（组件/E2E/视觉）+ 关键用例表
- **影响评估**：对现有前端影响 + 后端接口依赖 + UI Spec 生成指引表

#### 4c) 全栈交叉引用

全栈范围时，两份文档互相交叉引用：
- backend-design 头部的「关联前端设计」指向 frontend-design 文件路径
- frontend-design 头部的「关联后端设计」指向 backend-design 文件路径

### 5) 输出设计文档

根据范围分类，设计文档保存路径：

```
仅后端: docs/modules/<module>/design/<编号>-<slug>-backend-design.md
仅前端: docs/modules/<module>/design/<编号>-<slug>-frontend-design.md
全栈:   两个文件都生成
```

例如：`docs/feat/020-user-oauth.md`
- 仅后端 → `docs/modules/auth/design/020-user-oauth-backend-design.md`
- 仅前端 → `docs/modules/auth/design/020-user-oauth-frontend-design.md`
- 全栈 → 两个文件都生成

```bash
# 确保设计目录存在
mkdir -p docs/modules/<module>/design
```

> **注意**：
> - 详细的代码级验证由 `design-review-dev` skill 统一负责
> - 如 feat 涉及多个模块，在每个模块下生成对应的设计文档
> - 本 skill 聚焦架构层设计（接口/模型/逻辑/组件/状态），不写具体代码

### 6) 下一步建议

设计文档生成后，根据范围输出不同的下一步指引：

#### 仅后端

```
════════════════════════════════════════════════════════════════
✅ 后端设计文档已生成

📄 设计文档路径：docs/modules/<module>/design/<编号>-<slug>-backend-design.md

📌 下一步：使用 design-review-dev skill 进行设计 Review 后开发
   命令：/design-review-dev <设计文档路径>

💡 design-review-dev 将会：
   1. 验证设计文档的可实现性
   2. 检查依赖和代码一致性
   3. 生成开发任务清单
   4. 测试先行开发（先写测试再写业务代码）
════════════════════════════════════════════════════════════════
```

#### 仅前端

```
════════════════════════════════════════════════════════════════
✅ 前端设计文档已生成

📄 设计文档路径：docs/modules/<module>/design/<编号>-<slug>-frontend-design.md

📌 下一步：使用 design-review-dev skill 进行设计 Review 后开发
   命令：/design-review-dev <设计文档路径>

💡 design-review-dev 将会：
   1. 验证前端设计的组件结构、状态管理、路由完整性
   2. 检查 API 端点可用性和数据结构匹配
   3. 检查项目骨架（无则通过 ui-gen Phase 0 初始化）
   4. 从页面原型生成 UI Spec → ui-gen Phase 1/2 生成代码
   5. 组件测试 + E2E 测试
════════════════════════════════════════════════════════════════
```

#### 全栈

```
════════════════════════════════════════════════════════════════
✅ 全栈设计文档已生成（共 2 份）

📄 后端设计：docs/modules/<module>/design/<编号>-<slug>-backend-design.md
📄 前端设计：docs/modules/<module>/design/<编号>-<slug>-frontend-design.md

📌 建议开发顺序：先后端 → 后前端
   1. /design-review-dev <后端设计文档路径>   ← 先完成后端 API
   2. /design-review-dev <前端设计文档路径>   ← 再开发前端页面

💡 理由：前端依赖后端 API，先完成后端可确保前端对接真实接口
   如无阻塞依赖，也可并行开发（后端 TDD + 前端 ui-gen）
════════════════════════════════════════════════════════════════
```
