# Design Review & Development

## 目的

对设计文档 Review → 开发 → 代码审查 → 修复循环 → Feature E2E 验收，输出最终报告供人工审核。

## 工作流

```
1) 定位文档 → 2) 识别类型 → 3) Review检查 → 4) 代码探索验证 → 5) 输出Review结果
    ↓
6) 用户确认 → 7) 开发执行(后端TDD/前端ui-gen) → 7.5) 测试回归 → 8) 开发阶段报告
    ↓
9) 代码审查 → 10) 代码修复 → 11) 回归验证 ── 失败 → 返回步骤 10
    ↓ 通过
12) Feature E2E 验收（条件触发）── 失败 → 返回步骤 10
    ↓ 通过/跳过
13) 输出最终报告（含人工审核清单）
```

### 1) 定位文档

- 用户指定路径 → 直接读取
- 否则检查: `docs/modules/*/design/*-backend-design.md` / `*-frontend-design.md` / `docs/design/*-design.md` / `docs/fix/*.md`
- 优先最近修改的文档

### 2) 识别文档类型

| 类型 | 文件名特征 | Review 重点 |
|------|-----------|------------|
| backend-design | `*-backend-design.md` | API/模型完整性、依赖可用性、测试策略 |
| frontend-design | `*-frontend-design.md` | 组件结构、状态管理、路由、响应式 |
| design (旧) | `*-design.md`（无 backend/frontend 后缀） | 按后端处理 |
| fix | `fix-*.md` | 方案正确性、影响范围 |

**全栈检测**: 发现一种后缀时自动检查同目录是否有配对文档，有则提示用户先后端后前端。

### 3) Review检查

#### 3.1 后端设计 (backend-design / 旧格式 design / fix)

**可实现性**: 数据模型可落地、接口定义完整、依赖可用、代码结构合理
**代码验证**: 依赖方法签名匹配、目标文件存在、目录结构正确、无命名冲突
**测试策略**: 测试范围明确、可测试性评估、测试文件规划（缺少则作为警告）
**风险评估**: 复杂度高/依赖变更 → 影响时间估算/可能需要先修改被依赖模块

#### 3.2 修复文档 (fix)

**方案正确性**: 根因分析准确（有代码证据）、修复方案有效、无副作用、回归风险低
**代码验证**: 问题代码位置正确、修改方案可落地、目标代码自文档编写后未被修改

#### 3.3 前端设计 (frontend-design)

**架构可行性**: 组件结构合理、状态分层正确、路由完整、数据获取策略合理
**前端代码验证**: 目标目录存在、组件库可用、API 端点匹配、路由无冲突
**UI/UX 完整性**: 原型图完整、状态覆盖(加载/空/错误)、响应式说明、交互流程
**后端一致性**（有配对后端时）: API 路径/数据结构/错误码对齐

### 4) 代码探索验证

使用 Serena MCP 符号工具验证设计与代码一致性:
- `find_symbol` 查找设计中引用的类和方法
- `get_symbols_overview` 获取目标文件结构
- `find_referencing_symbols` 验证修改影响范围

- [ ] ...

| 序号 | 任务 | 文件 | 优先级 | 状态 |

**任务生成规则**:
- 每个业务代码任务后紧跟其测试任务，二者同优先级
- backend: 数据模型变更 → 迁移任务 + 测试任务；文件新增/修改 → 创建/修改任务 + 测试任务
- frontend: 骨架检查 → 共享基础设施(路由/布局/组件/状态/API) → 逐页面生成 → 集成验证 → 测试
- fix: 修改文件任务 + 测试任务 + 回归测试任务

### 6) 确认后开始开发

阻塞问题解决后确认开始开发，使用 TodoWrite 创建任务追踪。

### 7) 开发执行

#### 7a) 后端开发 (backend-design / 旧格式 design / fix)

**测试先行**: 先写单元测试（RED）→ 编写业务代码（GREEN）→ 运行测试 → 失败则修复后重试，通过后进入下一模块。

```
每个功能模块:
  ① 编写单元测试 → 确认失败(RED)
  ② 编写业务代码使测试通过(GREEN)
  ③ 运行该模块全量单元测试
  ④ 全部通过 → 标记完成 → 下一个模块
     失败 → 修改业务代码 → 回到③
```

**单元测试要求**:
- 每个新增/修改的公共方法都要有对应测试
- 测试独立、无顺序依赖、无外部依赖(DB/网络/文件)
- 遵循项目测试目录约定

**测试注释规范**（每个测试函数必须包含）:

| 字段 | 必填 | 说明 |
|------|------|------|
| `@doc` | Yes | 关联文档路径 |
| `@purpose` | Yes | 验证什么业务规则（写"验证折扣参与计算"而非"测试 calculate 方法"） |
| `@context` | Yes | 测试失败意味着什么、影响什么 |
| `@depends` | No | 依赖的关键方法 |

示例:
```go
// TestCreateUser_ReturnsUserID
// @doc     docs/feat/feat-023-user-management.md
// @purpose 验证创建用户时返回有效的用户 ID
// @context 用户注册流程的核心步骤；失败则说明 ID 生成策略被破坏，
//          直接影响注册、登录等下游功能
// @depends UserService.Create, IDGenerator.Next
func TestCreateUser_ReturnsUserID(t *testing.T) { ... }
```

**完成标准**: 所有任务完成 + 新增测试全部通过 + lint/typecheck/build 无错误。

#### 7b) 前端开发 (frontend-design)

通过 ui-gen 流程生成，先共享基础设施后逐页面填充:

```
① 项目骨架检查 → 无前端项目则 ui-gen Phase 0
② ui-gen Phase 1: 验证 frontend-design.md 完整性(§2-§8)，补全缺失信息
③ ui-gen Phase 2: 共享基础设施(路由/布局/组件/状态/API) → 逐页面(P0→P1→P2) → 跨页面集成
④ 组件测试 + E2E 测试
```

**完成标准**: 所有页面生成 + 关键共享组件有测试 + P0 流程有 E2E + 响应式正确 + build/lint 无错误。

### 7.5) 测试回归

#### 后端: 全量单元测试回归

运行项目全量单元测试 (`make test` / `npm run test` / `pytest` / `mvn test`)。

**失败分类**（用 `git stash` 对比判断）:
- **新增测试失败** → 必须修复代码直到全部通过
- **存量测试失败** → 输出失败用例分析清单，逐条说明原因和因果关系，不阻塞流程但用户必须看到

**存量测试失败清单格式**:
| # | 测试文件 | 用例名称 | 失败原因分类 | 原因说明 |
|---|----------|----------|-------------|----------|
| 1 | user_test.go:45 | TestGetUser | 本次变更导致 | 修改了 User.Name → FullName，存量断言旧字段名 |
| 2 | config_test.go:30 | TestLoadConfig | 变更前已失败 | stash 后仍失败，可能环境配置缺失 |

#### 前端: 全量前端测试回归

`npm run test` + `npx playwright test`，处理逻辑同上。

### 9) 代码审查

#### 9.1 静态分析

```bash
# Go: make lint && make typecheck
# Node.js: npm run lint && npm run typecheck
# Python: make lint && make typecheck
```

#### 9.2 人工审查清单

| 维度 | 检查项 |
|------|--------|
| 正确性 | 逻辑正确、边界处理、错误处理完整 |
| 安全性 | 输入验证、权限检查、敏感信息无泄露 |
| 性能 | 复杂度合理、并发安全 |
| 可维护性 | 命名规范、结构清晰、职责单一 |
| 测试覆盖 | 核心逻辑、边界、异常 |

**前端代码追加 Web Interface Guidelines**：
- 审查前端代码时，从 [web-interface-guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md) 拉取最新规则
- 按规则检查：无障碍（语义化 HTML/标签关联/可聚焦）、布局（间距一致/主内容区约束）、排版（标题层级/正文字号）、配色（语义色/每视口单 CTA）、组件（按钮层级/列表表格使用）

#### 9.3 问题分级

| 级别 | 标识 | 说明 | 处理 |
|------|------|------|------|
| Critical | 🔴 | 安全漏洞、数据丢失风险 | 必须立即修复 |
| Major | 🟠 | 功能错误、逻辑问题 | 必须修复 |
| Minor | 🟡 | 代码风格、命名 | 建议修复 |
| Info | 🔵 | 优化建议 | 可选 |

### 10) 代码修复

按优先级修复 (🔴 → 🟠 → 🟡 → 🔵)，每个修复记录:

| 问题ID | 级别 | 文件 | 问题描述 | 修复方案 | 状态 |
|--------|------|------|----------|----------|------|
| R-001 | 🔴 | auth.go:45 | SQL注入风险 | 使用参数化查询 | ✅ |

### 11) 回归验证

运行 lint + typecheck + 全量测试，确保 review 修复无副作用。**不写新测试**（新测试在步骤 7 完成）。

**通过标准**: lint/typecheck 无新增错误，全量测试通过数 ≥ 修复前。
**失败处理**: 修复引入的新回归 → 返回步骤 10；修复前就存在的失败 → 记录但不阻塞。**禁止注释/跳过测试来通过验证。**

### 12) Feature E2E 验收

> **数据来源**：设计文档的 E2E 测试用例（backend-design §5.2 / frontend-design §9.2）。
> 每条用例对应一条验收标准，由本步骤**逐条执行，直到全部通过**。

#### 12.1 触发条件

| 条件 | 处理 |
|------|------|
| 设计文档包含 E2E 测试用例（§5.2 / §9.2 有数据） | ✅ 执行 |
| 设计文档有测试策略但 E2E 用例为空 | ⚠️ 提示用户补充，跳过 |
| 仅内部逻辑变更（无页面、无外部接口） | ⏭️ 跳过 |

#### 12.2 执行与循环

```
从设计文档读取 E2E 测试用例
       │
       ▼
┌─────────────────────────────┐
│  逐条执行 E2E 测试用例       │
│  ├─ API 类: curl/httpie     │
│  └─ UI 类:  agent-browser   │
│       │                     │
│       ▼                     │
│  记录: ✅ 通过 / ❌ 失败     │
│  失败: 记录实际结果 + 证据   │
└──────────┬──────────────────┘
           │
           ▼
    ┌──── 全部通过？────┐
    │                   │
   YES                  NO
    │                   │
    ▼                   ▼
  输出报告    ┌─────────────────────┐
             │ 分析失败原因          │
             │ 返回步骤 10 修复代码  │
             │ 修复后重新执行本步骤  │
             │ （重新执行全部用例）  │
             └─────────────────────┘
```

**关键规则**：
- **全部通过才可进入步骤 13**，不允许跳过失败的用例
- 每次修复后**重新执行全部 E2E 用例**（不是只重跑失败的），确保无回归
- 修复循环超过 3 轮仍失败 → 输出详细报告，暂停并请用户介入
- ⚠️ AI 无法判断的结果（如视觉还原度）→ 标记需人工确认，不阻塞

#### 12.3 API 类 E2E（从 backend-design §5.2 读取）

使用 curl/httpie 按用例逐条执行：

| E2E ID | 验收标准 | 方法 | 路径 | Req | 期望 | 实际 | 结果 | 证据 |
|--------|---------|------|------|-----|------|------|------|------|
| E2E-001 | xxx | POST | /api/x | ... | 201 | 201 | ✅ | response body |

#### 12.4 UI 类 E2E（从 frontend-design §9.2 读取）

使用 agent-browser 按用例逐条执行：

| E2E ID | 验收标准 | 起始页面 | 操作 | 期望 | 实际 | 结果 | 截图 |
|--------|---------|----------|------|------|------|------|------|
| E2E-001 | xxx | /login | 填表→提交 | 跳转/dashboard | /dashboard | ✅ | shot-01.png |
