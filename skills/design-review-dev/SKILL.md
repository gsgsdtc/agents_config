# Design Review & Development

## 目的

- 在开发开始前，对设计文档（backend-design / frontend-design / 旧格式 design / fix）进行 Review
- 确保设计/修复方案的完整性、可执行性和与代码库的一致性
- 识别潜在的技术问题、遗漏或与现有代码的冲突
- 输出开发任务清单，便于追踪实现进度
- **后端设计**：业务代码开发完成后自动评估测试可运行性，条件满足时启用 ralph-loop 进行 TDD 测试验收
- **前端设计**：通过 ui-gen 流程生成页面代码，组件测试 + E2E 测试验收

## 工作流

### 整体流程概览

```

                     └─ 前端：组件/状态/路由/数据获取
```

### 1) 定位文档

- 如果用户指定了文档路径，直接读取
- 否则检查以下位置：
  - `docs/modules/*/design/*-backend-design.md` - 后端设计文档
  - `docs/modules/*/design/*-frontend-design.md` - 前端设计文档
  - `docs/design/*-design.md` - 设计文档（含旧格式）
  - `docs/fix/*.md` - 修复文档
- 优先选择最近修改的文档

### 2) 识别文档类型

| 类型 | 文件名特征 | Review 重点 |
|------|-----------|------------|
| backend-design | `*-backend-design.md` | API/模型完整性、依赖可用性、测试策略 |
| frontend-design | `*-frontend-design.md` | 组件结构、状态管理、路由、响应式 |
| design (旧格式) | `*-design.md`（无 backend/frontend 后缀） | 按后端处理（向后兼容） |
| fix | `fix-*.md` | 方案正确性、影响范围 |

**全栈检测**：发现一种设计后缀时，自动检查同目录是否存在配对文档：
- 发现 `*-backend-design.md` → 检查同目录是否有 `*-frontend-design.md`
- 发现 `*-frontend-design.md` → 检查同目录是否有 `*-backend-design.md`
- 如有配对，提示用户两份文档都需要 Review（建议先后端后前端）

### 3) 执行Review检查

#### 3.1 后端设计文档（backend-design / 旧格式 design）Review

**可实现性检查**
| 检查项 | 说明 |
|--------|------|
| 数据模型可落地 | 表结构定义完整，字段类型明确 |
| 接口定义完整 | 请求/响应结构清晰，错误码定义全 |
| 依赖可用 | 引用的服务/方法在代码库中存在 |
| 代码结构合理 | 新增/修改文件路径正确，职责清晰 |

**代码验证**
| 检查项 | 说明 |
|--------|------|
| 依赖方法签名匹配 | 设计中引用的方法签名与代码一致 |
| 目标文件存在 | 需要修改的文件确实存在 |
| 目录结构正确 | 新增文件的目录路径存在 |
| 无命名冲突 | 新增的类/方法不与现有代码冲突 |

**单元测试策略检查**
| 检查项 | 说明 |
|--------|------|
| 测试范围明确 | 设计文档中标注了需要测试的核心逻辑 |
| 可测试性 | 新增代码结构支持单元测试（依赖可注入、职责单一） |
| 测试文件规划 | 明确单元测试文件的位置和命名 |

> 如果设计文档缺少测试策略，作为**警告事项**输出，要求补充。

**实现风险评估**
| 风险项 | 影响 |
|--------|------|
| 复杂度高 | 影响开发时间估算 |
| 依赖变更 | 可能需要先修改被依赖模块 |

#### 3.2 修复文档（fix）Review

**方案正确性检查**
| 检查项 | 说明 |
|--------|------|
| 根因分析准确 | 问题原因定位正确，有代码证据 |
| 修复方案有效 | 修复逻辑能解决根本问题 |
| 无副作用 | 修复不会引入新问题 |
| 回归风险低 | 修改范围可控，影响评估完整 |

**代码验证**
| 检查项 | 说明 |
|--------|------|
| 问题代码位置正确 | 文档中引用的代码行号/内容匹配 |
| 修改方案可落地 | 建议的代码修改符合现有代码结构 |
| 相关代码无变更 | 自文档编写后，目标代码未被修改 |

#### 3.3 前端设计文档（frontend-design）Review

**架构可行性检查**
| 检查项 | 说明 |
|--------|------|
| 组件结构合理 | 层次清晰、职责单一、复用合理 |
| 状态分层正确 | 服务端/URL/表单/UI/全局状态界限清晰，无过度全局化 |
| 路由完整 | 路由表覆盖所有页面，无冲突，权限明确 |
| 数据获取策略合理 | SSR/CSR 选择有依据，加载/空/错误状态覆盖 |

**前端代码验证**
| 检查项 | 说明 |
|--------|------|
| 目标目录存在 | 前端项目目录结构正确 |
| 组件库可用 | 设计中使用的组件库已安装（shadcn/ui, Material 等） |
| API 端点匹配 | 前端依赖的 API 端点已存在或在配对后端设计中定义 |
| 路由无冲突 | 新增路由与现有路由无冲突 |

**UI/UX 完整性检查**
| 检查项 | 说明 |
|--------|------|
| 原型图完整 | 每个页面都有 ASCII 线框图 |
| 状态覆盖 | 加载态、空态、错误态都有设计 |
| 响应式说明 | 断点策略和适配方案明确 |
| 交互流程 | 关键交互有序列描述 |

**后端一致性检查**（有配对后端设计时）
| 检查项 | 说明 |
|--------|------|
| API 调用对齐 | 前端数据获取的 API 路径与后端设计一致 |
| 数据结构对齐 | 前端使用的数据结构与后端响应结构匹配 |
| 错误码对齐 | 前端错误处理覆盖后端定义的错误码 |

### 4) 代码探索验证（唯一入口）

> **设计原则**：代码级验证逻辑集中在此 skill，`feat-review-design` 不做代码验证。

使用 Serena MCP 的符号工具验证设计与代码的一致性：

```
验证流程：
设计文档 ──▶ 提取依赖列表 ──▶ 逐一验证存在性 ──▶ 验证签名匹配 ──▶ 输出验证结果
                │
                ├── 引用的服务/类
                ├── 调用的方法
                ├── 需要修改的文件
                └── 使用的数据结构
```

**验证工具使用**：
- `find_symbol` 查找设计中引用的类和方法
- `get_symbols_overview` 获取目标文件结构
- `find_referencing_symbols` 验证修改影响范围

```markdown
- 文档路径：xxx
- 配对文档：xxx（如有）

| 序号 | 任务 | 文件 | 优先级 | 状态 |
|------|------|------|--------|------|
```

#### 5.2 生成开发任务

从设计文档中提取并生成具体的开发任务。**单元测试任务与业务代码任务同优先级、同步生成。**

**backend-design / 旧格式 design 任务提取**：
- 数据模型变更 → 表结构/迁移任务 + **对应的单元测试任务**
- 新增文件 → 文件创建任务 + **对应的单元测试任务**
- 修改文件 → 代码修改任务 + **对应的单元测试任务**

**frontend-design 任务提取**：
- 项目骨架检查 → 骨架初始化任务（如需）
- 前端设计验证 → 验证 frontend-design.md 完整性
- 共享基础设施 → 路由 + 布局 + 共享组件 + 状态 + API 层
- 逐页面 → 按优先级排序的页面生成任务
- 跨页面集成 → 集成验证任务
- 测试 → 组件测试 + E2E 测试任务

**fix 任务提取**：
- 修改文件清单 → 逐文件修改任务 + **对应的单元测试任务**
- 回归验证 → **回归测试用例任务**

**任务排列规则**：
> 每个业务代码任务后紧跟其测试任务，二者同优先级。

### 6) 确认后开始开发

- 如果有阻塞问题，等待用户确认或修改文档
- 阻塞问题解决后，确认是否开始开发
- 开始开发时，使用 TodoWrite 创建任务追踪

### 7) 开发执行（按文档类型分流）

#### 7a) 后端开发（backend-design / 旧格式 design / fix）

按照开发任务清单，采用**测试先行**的方式逐模块完成开发。

> **核心原则**：测试代码的编写优先于业务代码。先根据设计文档编写单元测试（此时测试必然失败），再编写业务代码使测试通过。单元测试是与业务代码同级的资产，不是事后补充。

> **自循环保证**：运行单元测试失败时，**必须自动进入修复循环**——分析失败原因、修改业务代码、重新运行测试——直到该模块所有测试通过后，才可标记任务完成并进入下一个模块。

##### 7a.1 开发执行

```
开发流程（每个功能模块）:

┌──────────────────────────┐
│ 功能模块任务              │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ ① 编写单元测试(含注释)   │◀── 先写测试，定义预期行为
│    此时测试应当失败(RED)  │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ ② 编写业务代码           │◀─────────────────┐
│    使测试通过(GREEN)      │                  │
└────────────┬─────────────┘                  │
             │                                │
             ▼                                │
┌──────────────────────────┐    失败          │
│ ③ 运行单元测试           │─────────────────▶│
└────────────┬─────────────┘  修改业务代码    │
             │ 全部通过       后重试           │
             ▼
┌──────────────────────────┐
│ ④ 标记任务完成           │──▶ 下一个功能模块
└──────────────────────────┘

⚠️ 规则：
- 先写测试：根据设计文档中的接口定义和预期行为编写测试用例
- 测试先行确认：编写完测试后运行一次，确认测试处于失败状态（RED）
- 再写业务代码：编写最少的业务代码使测试通过（GREEN）
- 自循环：测试未全部通过时，修改业务代码后重新运行，不可跳过
- 每次循环都需重新运行该模块的全部单元测试
```

##### 7a.2 单元测试要求

| 要求 | 说明 |
|------|------|
| 覆盖范围 | 每个新增/修改的公共方法都必须有对应的单元测试 |
| 测试文件位置 | 遵循项目已有的测试目录约定 |
| 测试命名 | 清晰描述被测行为，如 `test_create_user_returns_user_id` |
| **测试注释** | **每个测试函数必须包含标准注释头（见 7a.2.1）** |
| 独立性 | 每个测试用例独立运行，无顺序依赖 |
| 无外部依赖 | 单元测试不依赖数据库、网络、文件系统等外部资源 |

##### 7a.2.1 单元测试注释规范（必须）

每个测试函数上方必须包含标准注释头，提供文档关联和上下文信息，便于后续失败时快速定位问题。

**注释字段**：

| 字段 | 必填 | 说明 |
|------|------|------|
| `@doc` | Yes | 关联文档路径（feat/fix 文档） |
| `@purpose` | Yes | 这个测试验证什么业务规则/行为 |
| `@context` | Yes | 为什么需要这个测试，失败意味着什么 |
| `@depends` | No | 依赖的关键业务逻辑或方法 |

**Go 示例**：

```go
// TestCreateUser_ReturnsUserID
// @doc     docs/feat/feat-023-user-management.md
// @purpose 验证创建用户时返回有效的用户 ID
// @context 用户注册流程的核心步骤；如果此测试失败，
//          说明用户创建逻辑或 ID 生成策略被破坏，
//          直接影响注册、登录等依赖用户 ID 的下游功能
// @depends UserService.Create, IDGenerator.Next
func TestCreateUser_ReturnsUserID(t *testing.T) {
    // ...
}
```

**Python 示例**：

```python
# @doc     docs/fix/fix-007.md
# @purpose 验证订单金额计算包含折扣
# @context 修复了折扣未参与计算的 bug；如果此测试失败，
#          说明折扣计算逻辑再次出现回归，
#          用户下单时会被收取未折扣的原价
# @depends OrderService.calculate_total, Discount.apply
def test_order_total_includes_discount():
    # ...
```

**TypeScript/JavaScript 示例**：

```typescript
/**
 * @doc     docs/feat/feat-035-data-export.md
 * @purpose 验证导出 CSV 时列顺序与配置一致
 * @context 数据导出的列顺序由用户配置决定；如果此测试失败，
 *          说明列排序逻辑被改动，导出文件的列顺序会与用户预期不符，
 *          影响下游数据处理流程
 * @depends ExportService.generateCSV, ColumnConfig.getOrder
 */
it('should export CSV columns in configured order', () => {
    // ...
});
```

**注释编写原则**：

- `@purpose`：一句话说明验证的业务规则，不是代码描述（写"验证折扣参与计算"而非"测试 calculate 方法"）
- `@context`：回答"如果这个测试挂了，意味着什么？会影响什么？"——帮助未来的开发者（或自己）在测试失败时快速理解严重性和排查方向
- `@doc`：使用相对路径，指向 `docs/feat/` 或 `docs/fix/` 下的文档

##### 7a.3 完成标准

| 检查项 | 要求 |
|--------|------|
| 任务清单 | 所有业务代码任务完成 |
| **新增单元测试** | **所有新增单元测试任务完成且通过** |
| 代码质量 | lint 无错误 |
| 类型检查 | typecheck 通过 |
| 编译/构建 | 项目可成功构建 |

> 新增单元测试未通过时，**不可进入**下一阶段。

#### 7b) 前端开发（frontend-design）

按照前端设计文档，通过 ui-gen 流程整体生成代码（先共享基础设施，后逐页面填充）。

```
前端开发流程：

┌──────────────────────────┐
│ ① 检查项目骨架            │
│    有前端项目？            │
│    ├── 有 → 继续          │
│    └── 无 → ui-gen Phase 0│
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ ② 验证前端设计完整性      │◀── ui-gen Phase 1
│    frontend-design.md     │    验证 §2-§8 完整性
│    补全缺失信息           │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ ③ 批量生成前端代码        │◀── ui-gen Phase 2
│    ┌──────────────┐       │    先共享基础设施
│    │ 共享基础设施  │       │    后逐页面填充
│    │ 逐页面生成    │       │
│    │ 跨页面集成    │       │
│    └──────────────┘       │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ ④ 组件测试 + E2E 测试     │
└──────────────────────────┘

⚠️ 规则：
- 共享基础设施（路由、布局、共享组件、状态、API 层）先于页面生成
- 按页面优先级顺序开发（P0 → P1 → P2）
- 每个页面生成后验证：渲染正确、API 对接、交互功能
- 跨页面集成验证：导航路径、数据传递、共享组件引用一致
- 响应式适配在每个页面完成后验证
```

##### 7b.1 项目骨架检查

检查前端项目是否已初始化：
- **Web**：检查 `package.json` 中是否有 Next.js/React 依赖
- **iOS**：检查 `Package.swift` 或 `.xcodeproj` 是否存在
- **Android**：检查 `build.gradle` 或 `build.gradle.kts` 是否存在

无项目骨架时，使用 `ui-gen Phase 0` 初始化。

##### 7b.2 前端设计验证

使用 `ui-gen Phase 1` 验证 frontend-design.md 的完整性：
- 验证 §2-§8 各章节的代码生成就绪度
- 补全缺失的必需信息（交互式）
- 确认后进入 Phase 2 代码生成

### 7.5) 测试回归

#### 后端：全量单元测试回归（必须）

> **核心原则**：新代码不能破坏已有功能。开发完成后必须运行项目全量单元测试，确保存量测试无回归。

##### 执行步骤

```bash
# 运行项目全量单元测试（根据项目类型选择）
make test          # Go
npm run test       # Node.js
pytest             # Python
mvn test           # Java
```

##### 回归结果处理

```
全量测试结果:
┌─────────────────────────────┐
│ 运行项目全量单元测试         │
└──────────────┬──────────────┘
               │
      全部通过？
      ┌────┴────┐
      │         │
     YES        NO
      │         │
      │         ▼
      │   ┌─────────────────────────┐
      │   │ 分类失败用例             │
      │   │ (git stash 对比)        │
      │   └──────────┬──────────────┘
      │              │
      │     ┌────────┴────────┐
      │     │                 │
      │  新增测试失败       存量测试失败
      │     │                 │
      │     ▼                 ▼
      │   必须修复代码     分析原因并输出
      │   直到全部通过     失败用例清单

      ◀─────┘                 │
      │                       │
      ▼                       ▼
┌─────────────────────────────────┐

└─────────────────────────────────┘
```

##### 失败分类方法

| 判断依据 | 新增测试（必须修复至通过） | 存量测试（输出分析清单） |
|----------|--------------------------|------------------------|
| `git stash` 后测试 | stash 后通过 → 本次变更引入 | stash 后仍失败 → 变更前已存在 |
| 失败测试涉及的文件 | 与本次修改文件有直接关联 | 与本次修改无关 |

##### 新增测试失败处理

新增的单元测试**必须修复到全部通过**，无例外：
- 修复业务代码或测试代码
- 重新运行全量测试
- 重复直到新增测试零失败

##### 存量测试失败处理

存量测试失败时，**必须输出失败用例分析清单**，逐条说明原因：

```markdown
### 存量单元测试失败清单

| # | 测试文件 | 用例名称 | 失败原因分类 | 原因说明 |
|---|----------|----------|-------------|----------|
| 1 | user_test.go:45 | TestGetUser | 本次变更导致 | 本次修改了 User 结构体字段名 `Name` → `FullName`，存量用例断言了旧字段名 |
| 2 | order_test.go:112 | TestCreateOrder | 本次变更导致 | 新增了 `validate()` 前置校验，存量用例未传入必填字段 `userId` |
| 3 | config_test.go:30 | TestLoadConfig | 变更前已失败 | 与本次变更无关，stash 后仍失败，可能是环境配置缺失 |
```

**失败原因分类**（必须二选一）：

| 分类 | 含义 | 处理方式 |
|------|------|----------|
| **本次变更导致** | 本次代码变更破坏了存量用例的前提条件 | 说明具体哪个变更导致了失败，以及存量用例需要如何调整 |
| **变更前已失败** | 与本次变更无关，`git stash` 后仍失败 | 说明可能的原因（环境、配置、历史遗留） |

**原因说明要求**：
- 不能只写"测试失败"，必须说明**因果关系**
- 本次变更导致的：说明是哪行代码、哪个改动导致了用例断言失败
- 变更前已失败的：说明判断依据（stash 验证结果）

#### 前端：全量前端测试回归

```bash
# 运行前端测试（根据项目类型选择）
npm run test       # 组件测试
npx playwright test # E2E 测试
```

处理逻辑与后端回归相同（新增失败必须修复，存量失败输出清单）。

##### 门控规则

- **新增测试失败**：必须修复代码直到通过，不可跳过
- **存量测试失败**：输出失败用例分析清单，不阻塞流程，但用户必须看到完整的原因分析
- **全量测试无法运行**（缺环境/配置）：作为警告输出，不阻塞，但在报告中标注
